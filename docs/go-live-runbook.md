# Production go-live runbook (QIN-24 #4 + #5)

Single ordered sequence to take Qintar from "all code shipped" to "charging real
customers." Everything referenced here is **already built and verified offline**
(billing QIN-24, onboarding/auth QIN-25): `tsc` clean, `next lint` clean,
`billing:smoke` 22/22, `onboarding:smoke` 18/18. What remains is operator
provisioning + a live click-through — there is no more app code to write.

> **Owner split.** Steps marked **[operator]** need real accounts/secrets only a
> human can create (tracked by the pending QIN-24 interaction
> `qin24:golive:operator-setup:1` + the HubSpot ask on QIN-20). Steps marked
> **[CTO]** I run once the secrets land. Never paste secrets into Paperclip — set
> them in the Vercel project env.

`SYNC_TRIGGER_SECRET` / `CRON_SECRET` (hex 32) · `BILLING_ADMIN_SECRET` (hex 32).

## 2. Phase 1 — test mode end-to-end (safe dry run)

1. **[operator]** Set the **test** Stripe keys (`sk_test_…`, `whsec_…`, the 3
   `price_…` test ids), HubSpot test-app creds, `DATABASE_URL`,
   `AUTH_SESSION_SECRET`. Reply on the QIN-24 interaction when done.
2. **[CTO]** Apply migrations: `DATABASE_URL=… npm run db:migrate` (0000–0003).
3. **[CTO]** Re-run offline gates: `npm run typecheck && npm run billing:smoke && npm run onboarding:smoke`.
4. **[CTO]** Live click-through against the deploy:
   - `/sign-up` → creates a user + `organizations` row (session cookie set).
   - `/onboarding` → connect HubSpot (`/api/hubspot/install` consent) → optional Slack.
   - `/onboarding/plan` → pick a tier → `POST /api/billing/checkout` → Stripe Checkout.
   - Pay with test card `4242 4242 4242 4242` (any future expiry/CVC).
   - Stripe fires `checkout.session.completed` + `customer.subscription.*` →
     `/api/billing/webhook` → `subscriptions` row becomes `status=active`, `plan=…`.
   - Land on `/dashboard`; confirm entitlement: `GET /api/billing/status` (session)
     returns `{ active: true, plan }`.
   - `POST /api/billing/portal` → Billing Portal opens (cancel/update card works).

✅ Gate to pass before Phase 2: a brand-new signup reaches `active` and the
dashboard reflects the plan, with no manual DB edits.

## 3. Phase 2 — flip to production

1. **[operator]** Swap every Stripe value for its **live** equivalent
   (`sk_live_…`, live `price_…`, a **live-mode** webhook endpoint signing secret).
2. **[operator/CTO]** Point the domain: set `NEXT_PUBLIC_SITE_URL=https://app.qintar.com`
   and `HUBSPOT_REDIRECT_URI=https://app.qintar.com/api/hubspot/callback`. Register
   that exact redirect URL on the HubSpot app and (if used) the Slack app.
3. **[operator]** In Stripe, create the **live** webhook endpoint →
   `https://app.qintar.com/api/billing/webhook` (events: `checkout.session.completed`,
   `customer.subscription.*`).
4. **[CTO]** Set `ENFORCE_ENTITLEMENTS=true` so non-paying orgs are gated.
5. **[operator]** Vercel: connect the custom domain (`app.qintar.com`) + DNS;
   disable Deployment Protection so the app is publicly reachable. `CRON_SECRET`
   stays set (HubSpot sync cron in `vercel.json` runs **daily** `0 6 * * *` —
   Hobby caps crons at once/day; on **Vercel Pro** raise it to e.g. `*/15 * * * *`).
   `npm run db:migrate` against the **prod** `DATABASE_URL`.

> **Deploy gotcha (fixed):** the first push of W2 failed the Vercel build because
> the cron was `*/15 * * * *`, which exceeds the Hobby once-per-day limit
> ("Deployment failed" → cron usage/pricing). Schedule is now daily; restore
> sub-daily only after upgrading the Vercel plan.

## 4. Post-flip verification

- Real signup on the prod domain → checkout with a **real card** (or your own,
  refund after) → `subscriptions` active.
- `customer.subscription.deleted` (cancel via Portal) → status flips, entitlement
  revoked.
- `GET /api/billing/status` reflects truth; `billing_events` shows processed ids
  with no duplicates.

## 5. Rollback

Set the Stripe env vars back to test keys (or unset) and `ENFORCE_ENTITLEMENTS=false`
to immediately stop charging while keeping the app up. No schema rollback needed —
the billing tables are additive.
